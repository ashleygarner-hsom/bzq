# BZQ Module Specifications and Standards

This document establishes the mandatory architecture, directory conventions, metadata contracts, and documentation standards required for all **BZQ ERP** modules and libraries.

---

## 1. Overview & Architectural Principles

BZQ ERP is engineered as a modular, extensible platform running entirely atop Google Workspace. Every capability—from core sequence generators to complex domain logic (e.g., Inventory, CRM, Billing)—is encapsulated in an isolated, self-describing **BZQ Module**.

### Core Tenets:
1. **Self-Describing Contracts**: Every module explicitly declares the business objects it introduces, their relational schemas, and default seed configurations.
2. **Deterministic Stable IDs**: Business objects are assigned permanent numeric stable IDs (`1000`, `2000`, `3000`, etc.) scoped by module ranges.
3. **Automated Compiler Verifiability**: Module structures, documentation, and schema definitions are strictly validated by the BZQ compiler during build and deployment.
4. **Code Cleanliness & Type Integrity**: Functions must adhere to strict size limits (max 20 lines, max 3 parameters, max 120 chars) with explicit schemas.

---

## 2. Mandatory Module Directory Layout

Every BZQ module directory must contain the following files:

```
<ModuleName>/
├── appsscript.json        # Google Apps Script manifest (dependencies, oauthScopes, runtime)
├── .clasp.json            # Clasp project bindings (scriptId, rootDir, projectId)
├── .claspignore           # Exclusion rules preventing local tooling from pushing to Apps Script
├── README.md              # Mandatory module specification and documentation
├── Objects.js             # Object metadata declarations & schema getter functions
├── Data.js                # Seed records & delta-seeding configuration data
└── <SourceFiles>.js       # Implementation classes, services, and UI components
```

## 3. Module `README.md` Specification

Every module MUST include a root `README.md`. The BZQ compiler verifies that the following sections are present:

### 3.1 Required Sections:
1. **Title & Summary Header**: `# <Display Name> (<ModuleName>)`
2. **Section 1: Module Identity & Purpose**:
   - Programmatic Module ID (must match folder name and `Objects.js` getter suffix).
   - Display Name.
   - Allocated Stable ID Range (e.g., `4000` – `4999`).
   - Business Purpose summary.
3. **Section 2: Developer & Maintainer Information**:
   ```markdown
   - **Organization**: HSOM Advisors
   - **Email**: bzqinfo@hsomadvisors.com
   - **Address**: 
   - **Phone**: 
   ```
4. **Section 3: Module Dependencies**:
   - Table detailing required upstream modules and minimum stable ID ranges.
5. **Section 4: Architecture & Process Flows**:
   - Minimum of 3 inline **Mermaid** diagrams:
     - **Component Architecture** (`graph TD` or `graph LR`)
     - **Sequence Diagram** (`sequenceDiagram` with `autonumber`)
     - **Process Flow** (`flowchart TD`)
6. **Section 5: Module BZQ Objects**:
   - Markdown table summarizing all objects defined in `Objects.js` (Object Name, Stable ID, Full Stable ID, Datasheet, Primary Key Fields, ID Field, Sequence Prefix, Description).
   - Direct relative link to [`Objects.js`](./Objects.js).
7. **Section 6: Development & Deployment**:
   - Standard CLI instructions for pushing and deploying the module.

## 4. `Objects.js` Metadata Contract

The `Objects.js` file serves as the single source of truth for object schemas introduced by a module.

### 4.1 Root Export Contract
Every module must export a global getter function following the naming convention `getObjects_<ModuleName>()`:

```javascript
/**
 * Returns the object metadata schema and unique stable IDs for the <ModuleName> module.
 * @returns {Array<Object>} List of object metadata definitions.
 */
function getObjects_<ModuleName>() {
  return [
    getObject_<ModuleName>_<StableId1>_(),
    getObject_<ModuleName>_<StableId2>_()
  ];
}
```

### 4.2 Individual Object Helper Contract
Each object is generated by a private helper function named `getObject_<ModuleName>_<StableId>_()`. It must return a structured object schema adhering to the following schema definition:

```javascript
/**
 * Returns metadata schema for <ObjectName> (<ModuleName>.<StableId>).
 * @private
 * @returns {Object}
 */
function getObject_<ModuleName>_<StableId>_() {
  return {
    Name: "Customer",                            // String: Object Name
    StableId: 4000,                              // Number: Unique stable ID
    FullStableId: "CustomerManagement.4000",     // String: {ModuleName}.{StableId}
    Datasheet: "Customers",                      // String: Google Sheet tab name
    Description: "Detailed business summary.",   // String: Functional description
    PrimaryFields: ["Customer Name"],            // Array<String>: Primary business keys
    IdFieldName: "Customer Number",              // String: Unique generated ID column
    Sequence: {                                  // Object | null: Numbering configuration
      Prefix: "xCU-",
      StartingNumber: 10000,
      Format: "0000#"
    },
    Indexes: ["Customer Name", "Email"],         // Array<String>: Indexed columns
    Fields: {                                    // Object: Field definitions
      "Customer Number": {
        type: "AUTOID",
        description: "Computed unique customer identifier",
        validation: null
      },
      "Customer Name": {
        type: "TEXT",
        description: "Primary customer business name",
        validation: "REQUIRED"
      },
      "Account Manager": {
        type: "LOOKUP",
        description: "Assigned staff member",
        references: "Staff.5000"
      },
      "Status": {
        type: "DROPDOWN",
        description: "Lifecycle status",
        validation: "DROPDOWN:Customer Status"
      }
    }
  };
}
```

### 4.3 Field Types:
- `AUTOID`: Auto-generated unique sequence identifier.
- `TEXT`: Standard string or descriptive text.
- `NUMBER`: Numeric values (integers or floating point).
- `BOOLEAN`: Boolean toggle (`true`/`false`).
- `DATE`: ISO Date or Google Sheets date value.
- `LOOKUP`: Foreign key reference to another BZQ object.
- `DROPDOWN`: Scoped or global dropdown selection.
- `CURRENCY`: Financial currency value.
- `JSON`: Serialized structured JSON metadata.

## 5. `Data.js` Seeding Conventions

Every module provides default seed configuration and initial worksheet records via `getSeedData_<ModuleName>()`.

### 5.1 Structure & Rules:
1. **Delta-Seeding Core Objects**:
   - Modules seed records into upstream core objects using the `{ModuleName}.{StableId}` syntax (e.g., `"AppsUtilities.1000"` for Sequences, `"AppsUtilities.1001"` for Objects).
2. **Local Object Seeding**:
   - Modules seed initial rows into their own objects using their local stable ID key (e.g., `"4000"`).
3. **Stable-ID Relational Binding**:
   - Foreign keys in seed data resolve against stable IDs or filter queries (e.g., `"AppsUtilities.1001.filter(Object Name == 'Customer')"`).

## 6. Future BZQ Compiler Validation Rules

When module validation is executed during the build pipeline (`./bzq compile` or CI/CD), the compiler will enforce the following static assertions:

| Check Code | Assertion Description | Severity |
| :--- | :--- | :--- |
| **`MOD-001`** | Module directory contains `README.md`, `Objects.js`, `Data.js`, `appsscript.json`. | **BLOCKING ERROR** |
| **`MOD-002`** | `README.md` contains all required sections, developer contact info, and 3 Mermaid diagrams. | **BLOCKING ERROR** |
| **`MOD-003`** | `Objects.js` exports `getObjects_<ModuleName>()` and follows `getObject_<ModuleName>_<StableId>_()` helpers. | **BLOCKING ERROR** |
| **`MOD-004`** | All `StableId` values fall within the module's allocated range and are globally unique across repository. | **BLOCKING ERROR** |
| **`MOD-005`** | Every object contains non-empty `Description`, `PrimaryFields`, `IdFieldName`, `Indexes`, and `Fields`. | **BLOCKING ERROR** |
| **`MOD-006`** | All foreign key references in `Fields` resolve to valid declared objects. | **BLOCKING ERROR** |
| **`MOD-007`** | No function exceeds 20 lines, 3 positional parameters, or 120 characters per line. | **BLOCKING ERROR** |
| **`MOD-008`** | Diagrammatic Coverage: All exported classes, services, and schemas must appear in module diagrams. | **BLOCKING ERROR** |
| **`MOD-009`** | Governance Integrity: Deferred/TBD items must use structured `// TODO(ROADMAP-<ID>)` and registered in roadmap. | **BLOCKING ERROR** |

## 7. Spec-Driven & Diagram-First Development Standards

BZQ ERP enforces **Spec-Driven Development (SDD)** across all modules. Every architectural component and functional workflow must be modeled in text-based Mermaid diagrams prior to or concurrently with implementation.

### 7.1 Mandatory Diagram Types:
1. **Component Architecture (`graph TD` / `graph LR`)**:
   - Illustrates internal module classes, configuration dependencies, and boundary interactions with upstream libraries.
2. **Sequence Diagrams (`sequenceDiagram` with `autonumber`)**:
   - Traces step-by-step execution across user interactions, add-on entrypoints, service layers, and Google APIs.
3. **Process Flowcharts (`flowchart TD`)**:
   - Models business decision trees, error handling paths, and state transitions.

### 7.2 Atomic Synchronization Rule:
No code modification may be committed without updating its corresponding diagrams in `README.md` and related Diátaxis guides. Diagrams are living architectural contracts that guide both human developers and autonomous AI agents.

## 8. Future Needs, TBD Features & Roadmap Governance

Whenever an engineering change identifies an edge case, deferred optimization, or future capability (TBD):

1. **Source Code Annotation**:
   - Must use structured TODO comments linking to a roadmap identifier:
     ```javascript
     // TODO(ROADMAP-SEC-01): Implement automated token rotation before deployment to public Marketplace.
     ```
2. **Roadmap Registration**:
   - Must be logged in [`docs/ADDON_LIFECYCLE_ROADMAP.md`](./ADDON_LIFECYCLE_ROADMAP.md) (or module-specific roadmap) under the **Backlog & Future Initiatives** registry with:
     - Tracking ID (`ROADMAP-XXX-YY`)
     - Target Phase / Milestone
     - Scope & Impact Description
     - Code File References

---

## 9. Deprecation, Sunsetting & Obsolescence Lifecycle

When replacing or retiring legacy interfaces, functions, or schemas:

1. **JSDoc `@deprecated` Annotation**:
   - Deprecated symbols must declare both the deprecation date and the earliest safe removal date:
     ```javascript
     /**
      * @deprecated Deprecated on 2026-09-01. Obsolete and safe to remove on or after 2027-03-01.
      * Use SpreadsheetRegistry.lookupSpreadsheet() instead.
      */
     ```
2. **Minimum Sunsetting Window**:
   - A minimum of 6 months must elapse between deprecation and physical code deletion to ensure smooth tenant transitions.
